## 1. Sécurité

### S1 — Anciens secrets dans l'historique git 🔴
`backend/.env` a été versionné dans 13 commits (février 2026) avant d'être retiré. Il reste lisible par toute personne ayant accès au dépôt (`git log -p -- backend/.env`). Il contient notamment :
- `JWT_SECRET` (clé qui signe les sessions) ;
- `EMAIL_PASSWORD` du compte SMTP Zoho `contact@…` ;
- `FEDAPAY_SECRET_KEY` (clé sandbox `sk_sandbox…`) ;
- `PROD_DATABASE_URL` vers l'ancienne base Render.

**Risque** : si une de ces valeurs est encore utilisée en production, toute personne qui lit l'historique peut se fabriquer une session administrateur (JWT) ou envoyer des e-mails au nom de Hope.
**Action** : vérifier sur le VPS que `JWT_SECRET`, `REFRESH_TOKEN_SECRET` et le mot de passe Zoho sont **différents** de ceux de l'historique, sinon les changer (cela déconnecte tous les utilisateurs une fois). Supprimer l'ancienne base Render si elle existe encore. Réécrire l'historique n'est pas nécessaire une fois les secrets changés.

### S2 — Modification/suppression des données d'une autre agence 🔴
Une correction précédente (test `rlsOnly.ownerScope`) a filtré la **lecture** de ces modules par propriétaire, mais pas l'**écriture**. Ces routes cherchent l'élément par son seul numéro (`WHERE id = $1`) :

| Route | Fichier |
|---|---|
| `PUT` / `DELETE /api/providers/:id` | `providerRoutes.ts:154,174` |
| `PUT` / `DELETE /api/service-contracts/:id` | `serviceContractRoutes.ts:95,115` |
| `DELETE /api/expenses/:id` | `expenseRoutes.ts:217` |
| `PUT /api/tickets/:id`, `POST /:id/reschedule`, `POST /:id/close` | `ticketRoutes.ts:208,219,245,274` |

Le dépôt ne contient de règle RLS que pour `buildings` et `lots` (lecture publique). Le code lui-même indique que le rôle DB peut contourner la RLS.
**Risque** : un gestionnaire connecté peut supprimer les dépenses, prestataires ou contrats d'une autre agence, ou clôturer ses interventions, en changeant simplement le numéro dans la requête.
**Action** : ajouter le filtre `scopeByOwner()` déjà utilisé sur les lectures, avec un test par route.

### S3 — Modèles de documents partagés entre toutes les agences 🔴
La table `document_templates` n'a pas de colonne propriétaire. `GET/PUT/DELETE /api/templates` (`templateRoutes.ts`) agit sur **tous** les modèles, y compris « Contrat de Location Standard » et « Quittance de Loyer Simple », pour tout utilisateur ayant le droit d'écrire sur les documents.
**Risque** : une agence peut modifier ou supprimer le modèle de contrat utilisé par toutes les autres.
**Décision** : chaque agence a-t-elle ses propres modèles (copie des modèles par défaut) ? Ou bien les modèles par défaut deviennent-ils en lecture seule, modifiables par l'administrateur Hope uniquement ?

### S4 — Webhook d'abonnement FedaPay 🔴
`/api/webhooks/fedapay` (`fedapayWebhookRoutes.ts`) :
- **En production** (`FEDAPAY_MODE=live`), seules les adresses `127.0.0.1` sont acceptées. FedaPay est donc toujours refusé (403), et l'abonnement n'est activé que si l'utilisateur revient sur la page de vérification (`check-payment`).
- **En mode sandbox**, la vérification d'adresse est désactivée, et le contenu du webhook est cru sans être revérifié auprès de FedaPay, ni sur le montant. N'importe qui peut alors envoyer un faux « paiement approuvé » et activer un abonnement payant pour un compte de son choix.

**Action** : faire comme les webhooks des loyers et des dons, qui revérifient la transaction auprès de l'API FedaPay et retirent la liste d'adresses. Contrôler aussi que le montant correspond au prix de l'offre.

### S5 — Envoi de messages au nom de Hope 🟠
`POST /api/messages` (`messageRoutes.ts`) : tout compte connecté (locataire compris) peut envoyer un e-mail ou un WhatsApp à **n'importe quel** `recipient_id`, avec un contenu HTML non échappé, depuis l'adresse officielle.
**Risque** : spam ou hameçonnage crédible (« Hope Gestion vous demande de payer ici… »), et réputation de l'adresse d'envoi.
**Action** : n'autoriser que les destinataires liés à l'expéditeur (même ticket ou tâche, même propriétaire) et échapper le HTML.

### S6 — Dépendances vulnérables 🟠
L'audit T-018 (octobre) n'a jamais été appliqué.
- **Backend** : 2 critiques (`proxy-addr`, `fast-xml-parser`) et 15 hautes, dont `multer`, `express-rate-limit`, `path-to-regexp` et `nodemailer`. Presque toutes se corrigent par `npm audit fix` sans changement majeur. `nodemailer` demande un passage à la version 10, à tester. `fedapay` embarque un `axios` vulnérable, sans correctif disponible.
- **Frontend** : 1 critique (`jspdf`) et 8 hautes (`dompurify`, `react-router`, `axios`…).

**Action** : `npm audit fix` des deux côtés, puis build, tests et vérification des PDF et de la connexion.

### S7 — Fichiers en accès public par lien 🟡
Les fichiers envoyés sur Spaces le sont avec `ACL: 'public-read'`. Les noms sont aléatoires (UUID), donc impossibles à deviner, mais **un lien transmis donne un accès permanent**, sans connexion. Cela concerne aussi les pièces d'identité et les baux signés. `getSignedUrl()` (lien temporaire) existe mais n'est jamais utilisé. En mode stockage local, nginx sert aussi `/uploads/` sans contrôle.
**Décision** : passer les documents sensibles (pièces, baux, quittances) en privé avec des liens temporaires, et laisser les photos de biens en public.

### S8 — En-têtes de sécurité et documentation API 🟡
- Helmet (HSTS, CSP, anti-iframe) ne s'applique qu'à `/api`. Les pages du site servies par nginx n'en ont aucun.
- `/api/docs` (Swagger) est public et décrit toute l'API.
- `nginx/hopegestion.conf` : la règle des images statiques (`\.(png|jpg…)$`) passe avant `location /uploads/`. Les photos stockées en local peuvent donc renvoyer une erreur 404 (à confirmer selon la config réelle du VPS).

### S9 — Code de vérification e-mail 🟢
Code à 6 chiffres (`Math.random`), sans compteur d'essais par compte. La seule protection est la limite de 20 échecs par adresse IP toutes les 15 minutes. Risque faible : ce code ne sert qu'à activer un compte.

## 2. Performance

### P1 — Connexions à la base de données (piste principale de BUG-001) 🟠
`tenantGuard` ouvre une connexion dédiée (`pool.connect()`) pour **chaque** requête et la garde jusqu'à la fin de la réponse. Le pool est limité à **10** connexions (`db/database.ts`), avec 10 s d'attente maximum. Une page du tableau de bord déclenche plusieurs appels en parallèle. Avec quelques utilisateurs ou onglets ouverts en même temps, les requêtes suivantes **attendent**, puis échouent au bout de 10 s.
**Action** : mesurer d'abord sur le VPS (`SELECT count(*) FROM pg_stat_activity`, temps de réponse dans les logs). Ensuite, augmenter `DB_POOL_MAX` selon `max_connections` du serveur, et ne réserver une connexion dédiée qu'aux routes qui en ont besoin.

### P2 — Images des pages publiques 🟡
8 images PNG de 0,5 à 1 Mo chacune, soit **5,8 Mo** : photo d'accueil, famille, biens de démonstration, photos de l'équipe sur « À propos ». En 3G, la page d'accueil met plusieurs secondes à s'afficher.
**Action** : les convertir en WebP ou JPEG optimisé, soit environ 100 à 150 Ko chacune (-90 %).

### P3 — Index manquants 🟡
Les listes filtrent sur `owner_id`, mais aucun index n'existe sur `buildings`, `lots`, `tenants`, `payments`, `documents` ni `tickets`. L'impact est nul avec 135 lots, mais devient sensible à quelques milliers de lignes. Ajouter des index est sans risque.

### Ce qui est déjà correct
- JavaScript initial d'environ 210 Ko compressé ; pages chargées à la demande (71 pages) ; générateur PDF chargé seulement quand il sert.
- Cache des propriétaires autorisés (5 min), gzip activé dans nginx, cache long des fichiers compilés.
- Listes de biens et de lots en une seule requête, sans requêtes en cascade. Pas encore paginées : à surveiller au-delà d'environ 1 000 lots.
- Le chat interroge le serveur toutes les 5 s : à espacer si l'usage augmente.

## 3. Fiabilité & code

### F1 — Confirmation des loyers payés en ligne 🔴
`/api/rent-payments/webhook` est monté derrière `protect` (`index.ts`), qui exige d'être connecté. FedaPay n'envoie pas de jeton, donc il reçoit toujours une erreur 401. Le traitement prévu (revérification, mise à jour de l'échéance, quittance) ne s'exécute jamais à partir du webhook. Même problème pour les abonnements (voir S4).
**Action** : rendre ce chemin public, comme `/api/donations/webhook` (le code revérifie déjà la transaction auprès de FedaPay). Vérifier aussi l'adresse de webhook configurée dans le tableau de bord FedaPay.

### F2 — Sauvegardes 🔴
Aucun script de sauvegarde (`pg_dump`, cron) dans le dépôt. Le fichier de suivi indique TECH-001 « Sauvegardes automatisées » à 90 %.
**À confirmer sur le VPS** :
- une sauvegarde quotidienne existe ;
- elle est copiée **hors du VPS** ;
- une restauration a déjà été testée.

Sans cela, une panne du disque fait perdre toutes les données des clients.

### F3 — Tests 🟠
- Backend : **21 tests en échec sur 435** (5 suites) sur `main`. Ce sont des tests périmés : mock de `FinanceService` qui ne correspond plus à la route, cache de `tenantGuard` non vidé entre les tests. La suite ne peut donc plus servir d'alerte.
- Frontend : aucun test.

**Action** : remettre la suite au vert, puis la lancer automatiquement avant chaque déploiement.

### F4 — Déploiement 🟠
`.github/workflows/deploy.yml` :
- aucun test ni vérification de types avant la mise en production ;
- `rm -rf dist` avant le build : si le build échoue, le backend n'a plus de fichiers à relancer au prochain redémarrage ;
- le frontend est reconstruit **dans le dossier servi** : le site est cassé (pages blanches) pendant le build, environ 15 à 30 s à chaque fusion ;
- une migration en échec est ignorée (« non bloquant ») ;
- pas de retour rapide à la version précédente.

**Action** : construire dans un dossier temporaire puis basculer d'un coup, lancer `tsc` et les tests avant, et garder la version précédente.

### F5 — Création de bail non atomique 🟡
`POST /api/locations` (`leaseRoutes.ts`) enchaîne 4 opérations sans transaction : création du bail, numéro de référence, statut du lot, échéancier. Si une étape échoue, il reste un bail à moitié créé (sans référence ou sans échéancier) et un lot marqué occupé.
**Action** : envelopper ces opérations dans `BEGIN`/`COMMIT`.

### F6 — Journaux et alertes 🟢
Les journaux passent par `console.log` (PM2). Il n'y a ni niveau de gravité, ni alerte en cas d'erreur serveur, ni gestionnaire `unhandledRejection`. Une panne n'est découverte que lorsqu'un client la signale.
