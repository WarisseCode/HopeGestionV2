### T-000 : État initial du projet
- **Date** : 2026-09-23
- **Statut** : Terminée
- **Type** : Documentation

**Objectif et périmètre.** HopeGestionV2 est une application web de gestion immobilière (Bénin, Cotonou notamment) : gestion des biens (immeubles/lots), locataires, baux, paiements de loyer, dépenses, documents, états des lieux, mobile money, avec des tableaux de bord différenciés par rôle (gestionnaire/manager, propriétaire, locataire, admin). Un client mobile Flutter dédié (`HopeGestionMobile`, dépôt séparé) consomme une partie de cette même API via des routes `/api/auth/mobile/*` isolées du flux web (cookies httpOnly côté web, JSON pur côté mobile — voir T-004 à T-006 ci-dessous, chantier mené depuis le dépôt mobile). Monorepo avec deux applications indépendantes : `backend/` et `frontend/`.

**Stack technique.**
- Backend : Node.js (≥20.10), Express 5, TypeScript, PostgreSQL (`pg`, requêtes paramétrées, pas d'ORM), JWT (`jsonwebtoken`) + refresh tokens en base, `bcrypt`, `multer` (upload, stockage mémoire), Digital Ocean Spaces (`@aws-sdk/client-s3`) avec repli disque local en dev, `helmet`/`express-rate-limit`/`cors` pour le durcissement, `express-validator`, `nodemailer` (emails transactionnels/OTP), `node-cron` (tâches planifiées), `pdfkit`/`exceljs` (génération de documents), `twilio`/`fedapay` (intégrations tierces — usage exact à confirmer), tests avec `jest`+`supertest`+`ts-jest`.
- Frontend : React 19, Vite 7, TypeScript, TailwindCSS 4 + DaisyUI (le `README.md` racine mentionne encore "Material-UI", obsolète — vérifié dans `package.json`, c'est Tailwind/DaisyUI), TanStack Query (état serveur), React Router 7, `axios`/`fetch` mixtes selon les fichiers, `framer-motion`, `recharts`, `i18next` (multilingue), `react-signature-canvas` (signatures états des lieux), Storybook (composants UI).
- Déploiement : plusieurs docs présentes (`DEPLOYMENT.md`, `RAILWAY_DEPLOYMENT.md`, `OVH_DEPLOYMENT.md`, `CUSTOM_DOMAIN_SETUP.md`) suggérant une migration progressive d'hébergeur — Render mentionné comme cible historique (disque persistant évoqué dans le code d'upload), Railway et OVH comme cibles plus récentes (à confirmer laquelle est active en production aujourd'hui). Domaine de production observé dans le code : `hopegestion.com`.

**Modules/fonctionnalités présents (déduit des routes montées dans `backend/index.ts`)** : authentification (email/mot de passe + Google OAuth + comptes invités), profil/compte, biens (immeubles/lots), locataires, baux/locations, paiements, dépenses, documents (upload + génération PDF de baux/quittances), tableaux de bord par rôle, délégations d'accès, calendrier, audit-logs, mobile money, notifications, accès locataire (portail), alertes, permissions (matrice), affectations utilisateur↔propriétaire, finances, prêts (loans), tickets (interventions), inventaires/états des lieux (EDL) avec signature électronique, réservations publiques (page vitrine), CGU, invitations, upload de fichiers centralisé, mode maintenance avec token d'urgence.

### T-002 : Diagnostic — RLS bloque `POST /api/biens/lots` (`new row violates row-level security policy for table "lots"`) — non concluant, accès base de données requis
- **Date** : 2026-09-24
- **Statut** : Modifiée (voir T-003) — diagnostic complété par l'utilisateur (`\d+ lots`/`\d+ buildings` exécutés côté production) puis corrigé
- **Type** : Documentation
- **Description** : Investigation du 500 signalé en production sur `POST /api/biens/lots` (création de lot, juste après une création d'immeuble réussie sur le même compte). Comparaison structurelle du code de `POST /api/biens/immeubles` (fonctionne) et `POST /api/biens/lots` (échoue) — aucune différence trouvée qui expliquerait le rejet RLS côté applicatif. N'a pas pu aboutir : la politique RLS réelle sur `lots` n'existe dans aucun fichier versionné de ce dépôt, et aucun moyen de l'inspecter directement (base de données) n'est disponible dans cet environnement.
- **Vérifications effectuées (code réel)** :
  - `bienRoutes.ts` : `POST /immeubles` et `POST /lots` passent tous deux par le même middleware `tenantGuard` (résout `req.resolvedOwnerId`/`req.dbClient`, voir son code complet ci-dessous) puis insèrent `strictOwnerId = req.resolvedOwnerId` directement comme colonne `owner_id`, via `dbClient.query()` (jamais `pool.query()` — vérifié ligne par ligne sur toute la route `/lots`, y compris le repli `buildingRes` par nom d'immeuble). Aucune différence de mécanisme de session entre les deux routes.
  - `POST /lots` a un middleware supplémentaire avant `tenantGuard` — `checkPropertyLimit` (`middleware/subscriptionLimits.ts`) — mais celui-ci interroge `pool` (pas `req.dbClient`) pour un simple `COUNT`, avant que `tenantGuard` n'ouvre la connexion RLS-scopée de la requête : ne peut pas interférer avec la session utilisée ensuite pour l'`INSERT`.
  - `tenantGuard.ts` (relu en entier) : résout `resolvedOwnerId` identiquement pour les deux routes à partir de `owner_user` (0 lié : mode gestionnaire pur ; 1 lié : résolu automatiquement, indépendant du corps ; plusieurs : `owner_id` du corps requis). Pour un gestionnaire n'ayant qu'un seul propriétaire lié — cas le plus probable pour « un gestionnaire qui vient de créer l'immeuble parent avec succès » — `resolvedOwnerId` est résolu à l'identique pour les deux requêtes, indépendamment de ce que le corps contient.
  - Recherche exhaustive (`grep`) de toute définition de policy RLS sur `lots` dans le dépôt : une seule trouvée, `public_read_libre_lots` (migration `040_public_read_policies`, `FOR SELECT` uniquement, sans rapport avec un `INSERT`). Aucune trace de la fonction `get_current_owner_id()` (référencée en commentaire à plusieurs endroits, jamais définie dans ce dépôt) ni d'une policy `INSERT`/`WITH CHECK` sur `lots` ou `buildings` — confirme et étend le constat déjà posé en T-011/T-000 (dispositif RLS appliqué manuellement en base, jamais capturé dans une migration versionnée).
- **Décisions & justifications** : n'a délibérément **pas** tenté de deviner puis d'appliquer une commande `ALTER POLICY`/`DROP POLICY ... CREATE POLICY` sur `lots` sans avoir vu le texte réel de la policy actuelle — un correctif RLS mal ciblé sur une table de production risquerait soit de ne rien changer, soit d'affaiblir l'isolation multi-tenant sur une table sensible, pour un problème dont la cause exacte reste non confirmée.
- **Problèmes rencontrés** : bloqué avant toute conclusion, pour une raison identique à T-007 (`HopeGestionMobile/docs/JOURNAL_PROJET.md`) déjà rencontrée sur ce projet : aucune base PostgreSQL n'est joignable depuis cet environnement (`DB_HOST=localhost`, testé avec un script Node minimal utilisant `pg` directement — connexion refusée) et `psql` n'est pas installé. Même si une base locale était joignable, T-008 a déjà établi que le schéma de production (avec ses policies RLS manuelles) n'est pas reproductible localement à partir de `db/init.sql` + migrations seules — une inspection locale ne montrerait donc pas la policy réellement active en production. **Aucun code modifié.** Pour débloquer ce point (marqué priorité absolue par l'utilisateur), il faut soit le texte réel de la policy (`\d+ lots` en psql contre la base de production, à exécuter et coller par l'utilisateur), soit un accès en lecture à cette base fourni autrement. Pas de commit ni de push (rien à commiter). **STOP** sur ce point précis, en attente de cette information — voir la question posée en fin de réponse côté session mobile.

### T-003 : Correctif — `POST /api/biens/lots` insère désormais `owner_id` hérité de l'immeuble parent
- **Date** : 2026-09-24
- **Statut** : Terminée
- **Type** : Correction
- **Description** : Complète T-002. L'utilisateur a exécuté `\d+ lots`/`\d+ buildings` contre la production : la policy `tenant_isolation_policy` (`ALL`, sans `WITH CHECK` dédié — `USING` sert donc aussi de condition d'insertion) exige `owner_id = get_current_owner_id()` sur `lots`, comme sur `buildings`. `lots.owner_id` est nullable, sans défaut. Diagnostic demandé confirmé par lecture directe du code : `owner_id` **était bien présent** dans la requête `INSERT INTO lots (...)` (2ᵉ colonne), mais sa valeur (`req.resolvedOwnerId`, résolue par `tenantGuard` à partir de la session de LA requête courante) pouvait être `NULL` dans des cas où l'immeuble parent, lui, avait déjà un `owner_id` non-NULL bien défini — notamment un gestionnaire gérant plusieurs propriétaires, où `tenantGuard` exige un `owner_id` explicite dans le corps de **chaque** requête individuellement pour le résoudre (sinon `NULL`), alors que rien n'obligeait le client (mobile ou web) à le refournir pour créer un lot. Puisque `NULL = get_current_owner_id()` n'est jamais vrai en SQL (comparaison à `NULL`, jamais l'égalité), la policy RLS rejetait systématiquement l'insertion dans ce cas — d'où le message « new row violates row-level security policy ».
- **Fichiers touchés** : `backend/routes/bienRoutes.ts` (`POST /lots`), `backend/tests/routes/bien.test.ts` (nouveau, 3 tests).
- **Décisions & justifications** :
  - `owner_id` d'un lot est désormais toujours lu depuis l'immeuble parent (`SELECT owner_id FROM buildings WHERE id = $1`, via `dbClient` donc RLS-scopée) plutôt que dérivé de `req.resolvedOwnerId` — conforme à la remarque de l'utilisateur : un lot n'a aucune raison d'exiger que le client reconnaisse/refournisse un `owner_id` qu'il ne connaît de toute façon pas séparément de l'immeuble auquel il appartient. S'applique à la fois à la création (`INSERT`) et à la modification (`UPDATE ... owner_id = $20`, même variable, même défaut corrigé au passage pour rester cohérent — l'utilisateur n'avait pas explicitement demandé ce second cas mais laisser le même bug sur la modification aurait été incohérent avec la correction demandée).
  - Effet de bord positif, signalé pour transparence (non demandé explicitement mais découvert en écrivant le correctif) : cette même lecture sert aussi de vérification d'existence/autorisation sur `targetBuildingId` avant l'`INSERT`/`UPDATE` — un `building_id` inexistant ou appartenant à un autre tenant renvoie déjà 0 ligne (RLS), retournant un 400 explicite au lieu de tenter une écriture qui aurait de toute façon échoué. Avant ce correctif, un `building_id` fourni directement par le client (cas normal, pas le repli par nom) n'était jamais vérifié explicitement avant l'`INSERT` — seule la policy RLS sur `owner_id` protégeait indirectement contre un rattachement à l'immeuble d'un autre tenant.
  - **Donnée existante potentiellement affectée, signalée sans correction** : impossible de vérifier depuis cet environnement (toujours aucun accès base de données) s'il existe en production des lots avec `owner_id NULL` créés avant ce correctif (échoués silencieusement en 500, donc a priori **aucun** — un lot avec `owner_id NULL` n'aurait jamais pu être inséré du tout, la policy RLS l'aurait bloqué exactement comme le cas signalé). Aucune donnée corrective à appliquer a priori, mais à confirmer par l'utilisateur avec un accès direct à la base (`SELECT id FROM lots WHERE owner_id IS NULL`) avant de considérer ce point définitivement clos.
  - **Point contribuant côté mobile, non corrigé ici (hors périmètre de cette demande, backend uniquement)** : `HopeGestionMobile`'s `BiensRepository.createLot()`/`NouveauLotScreen` n'exposent aucun paramètre `owner_id` (contrairement à `createImmeuble()`) — c'est très probablement ce qui a déclenché ce bug pour un compte gestionnaire multi-propriétaires en pratique (aucune requête de lot n'a jamais pu fournir l'`owner_id` que `tenantGuard` aurait exigé). Ce correctif backend rend ce point sans conséquence (l'héritage depuis l'immeuble ne dépend plus du corps de la requête), donc aucune modification mobile n'est nécessaire suite à ce correctif précis — signalé pour mémoire seulement.
- **Tests** : `backend/tests/routes/bien.test.ts` (nouveau) — succès avec `owner_id` hérité de l'immeuble (`resolvedOwnerId` mocké à `null`, prouve qu'il n'est plus utilisé) ; immeuble introuvable/non visible par RLS → 400, aucun `INSERT` tenté ; `resolvedOwnerId` délibérément différent de l'owner réel de l'immeuble (simule un gestionnaire multi-propriétaires) → `owner_id` inséré reste bien celui de l'immeuble, pas `resolvedOwnerId`.
- **Problèmes rencontrés** : aucun. `npx tsc --noEmit` : propre. `npm test` : **100/105 tests verts**, 3 nouveaux tests verts inclus — les 5 échecs restants (`finance.test.ts`, `permissionMiddleware.test.ts`) sont l'état déjà documenté et inchangé depuis avant ce correctif (T-012 et suivants), sans rapport avec `bienRoutes.ts`. Pas de commit ni de push. **STOP**, comme demandé.
- **Remplace / modifie** : T-002 (complète le diagnostic resté bloqué, avec l'information fournie par l'utilisateur).
